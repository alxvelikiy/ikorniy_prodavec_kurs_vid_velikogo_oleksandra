# SUPABASE_SETUP — акаунти й прогрес (зрізи 1–2)

Покроково: створити проєкт Supabase, застосувати схему, отримати ключі, призначити роль «керівник», задати змінні в Netlify.

## 1. Створити проєкт

1. https://supabase.com → New project (на корпоративній пошті).
2. Регіон — будь-який ближчий; тариф Free вистачає для старту.
3. Дочекатись, поки проєкт підніметься (~2 хв).

## 2. Застосувати схему

1. У проєкті: **SQL Editor** → New query.
2. Вставити весь вміст файлу `supabase/migrations/0001_init.sql` із цього репозиторію → Run.
3. Новий запит → вставити весь вміст `supabase/migrations/0002_reset_and_attempts.sql` → Run (додає скидання прогресу й журнал спроб для кабінету наставника, зріз 2 — обов'язково ПІСЛЯ 0001).
4. Обидва мають відпрацювати без помилок (створюють таблиці `profiles`, `progress`, `attempts`, RLS-політики, тригери, функцію `reset_progress`).

Схему перевірено не лише синтаксично, а реальним прогоном на живому Postgres 16, включно з пастками, які вже виправлені в файлах:
- рекурсія RLS-політики (`profiles` перевіряла роль через підзапит до себе ж) — винесено в окрему функцію `is_mentor()`;
- захист від самопідвищення ролі спершу дивився не в те поле.

Деталі — `v2/mvp/tests/rls-test.sql` (15 сценаріїв: новачок бачить лише своє, не може писати в чужий прогрес, не може підвищити собі роль, керівник бачить усіх, але не може редагувати чужий прогрес напряму; наставник скидає прогрес (весь і по уроку) через `reset_progress`, новачок цю функцію викликати не може; журнал спроб — новачок пише і читає лише свої, наставник читає всі, ні новачок, ні наставник не можуть його редагувати чи видаляти (append-only)).

**Публічної реєстрації немає.** На сайті лишився тільки вхід — форми реєстрації (`account.html`) навмисно нема (перевіряє `account-e2e.mjs`, сценарій 1). Єдиний спосіб потрапити в курс — запрошення від керівника, див. крок 5.1 нижче. Це саме собою вимикає ризик випадкової/публічної реєстрації "з вулиці", тож перемикач **Authentication → Providers → Email → Confirm email** можна лишити як є (за замовчуванням увімкнено) — запрошений новачок і так переходить за посиланням з пошти, підтвердження відбувається тим самим переходом.

**Свій SMTP (не вбудований).** Вбудована пошта Supabase має низький ліміт (кілька листів на годину) — для запрошень кількох новачків підряд цього може не вистачити, лист просто не піде. Налаштувати власний SMTP:
1. **Project Settings → Auth → SMTP Settings** → увімкнути **Enable Custom SMTP**.
2. Вписати дані свого поштового провайдера (SMTP host/port/user/password, той самий, яким керівник уже користується на корпоративній пошті — Gmail, Outlook, або будь-який транзакційний сервіс на кшталт Resend/Postmark; усі підходять, Supabase лише ретранслює лист).
3. **Sender email** — адреса, з якої підуть листи-запрошення (варто узгодити з провайдером — деякі вимагають підтвердженого домену/адреси відправника).
4. Save, і надіслати собі тестове запрошення (крок 5.1), щоб перевірити, що лист доходить.

## 3. Отримати ключі

**Settings → API**:
- **Project URL** — це `SUPABASE_URL`.
- **anon public** ключ — це `SUPABASE_ANON_KEY`.

Обидва значення **публічні за задумом** Supabase (доступ обмежує RLS у базі, не секретність ключа) — їх безпечно вставляти в змінні збірки фронтенду. **service_role**-ключ (є на тій же сторінці) — секретний, він НІКУДИ в цей репозиторій і в жодну змінну збірки сайту не йде; знадобиться лише якщо колись знадобиться серверний скрипт для прямих адміністративних операцій в обхід RLS.

## 4. Задати змінні при збірці

Сайт (`node v2/build/build.mjs`) читає `SUPABASE_URL` і `SUPABASE_ANON_KEY` зі змінних оточення **під час збірки** (не в рантаймі браузера) і вшиває їх у `assets/supabase-config.js`. Без обох змінних акаунти вимкнені повністю — сайт працює як і раніше, офлайн, без жодного звернення до Supabase.

Локально:
```bash
SUPABASE_URL="https://xxxxxxxx.supabase.co" SUPABASE_ANON_KEY="eyJ..." node v2/build/build.mjs
```

На Netlify (коли дійдемо до зрізу 5 — деплою): **Site settings → Environment variables**, додати `SUPABASE_URL` і `SUPABASE_ANON_KEY`, вони підхопляться командою збірки автоматично.

## 5. Запросити новачка і призначити роль «керівник»

### 5.1. Запросити новачка (єдиний спосіб реєстрації)

1. Supabase → **Authentication → Users → Invite user**.
2. Вписати пошту новачка → Send invite. Лист іде через вбудовану пошту Supabase або свій SMTP (крок 2 вище).
3. Новачок переходить за посиланням з листа — відкривається `account.html` із формою «Встановити пароль» (те саме посилання, що й при відновленні пароля; перевірено в `account-e2e.mjs`, сценарій 1б). Роль «новачок» призначається автоматично, як і раніше.
4. Якщо лист не дійшов (ліміт вбудованої пошти) — надіслати ще раз із того самого пункту меню, або налаштувати свій SMTP (крок 2).

### 5.2. Призначити роль «керівник»

Роль підвищується **лише вручну через SQL Editor** — самостійно призначити собі роль «керівник» через сайт неможливо (перевірено тестом `rls-test.sql`, тест 4).

1. Керівник спершу сам проходить запрошення (крок 5.1, роль «новачок» призначиться автоматично).
2. У Supabase → **SQL Editor**:
   ```sql
   update public.profiles set role = 'mentor'
   where id = (select id from auth.users where email = 'кервник@пошта');
   ```
3. Керівнику потрібно перезайти на сайті (вийти/увійти або оновити сторінку), щоб побачити роль «керівник» на `account.html`.

## 6. Кабінет наставника (зріз 2)

`kerivnyku.html` (пункт меню «Керівнику») — коли акаунти ввімкнено, вгорі сторінки з'являється блок «Новачки (хмара)», видимий лише під акаунтом з роллю «керівник» (перевірка — на клієнті через `profiles.role`, дані ж реально захищені RLS: новачок і без цього блоку не отримає чужий прогрес/спроби мережевим запитом).

Для кожного запрошеного новачка кабінет показує:
- прогрес по днях і уроках (та сама таблиця, що й у «Прогрес на цьому пристрої», але з хмари для будь-якого новачка);
- дату останньої активності (`progress.updated_at`);
- історію спроб тесту уроку й тренажера — не лише останній/найкращий результат: кожна спроба (урок, дата, результат, помилки за кодами правил — без текстів відповідей) записується окремим рядком у `attempts` одразу з `finish()` (тест) чи вибору варіанта (тренажер);
- кнопки скидання: «Скинути урок» (прибирає лише `state.lessons[N]` — новачок ніби не проходив саме цей урок; повторення/симулятор/колода не чіпаються) і «Скинути весь прогрес» (повне очищення).

Скидання йде через `reset_progress(user_id, lesson_n)` — SQL-функцію з `0002_reset_and_attempts.sql`, що сама перевіряє роль виклику (лише «керівник»), і бампає **generation**: клієнт (`account.js`) звіряє своє локальне покоління з хмарним при кожному вході/відкритті сторінки — якщо хмарне більше, локальний кеш вважається застарілим і замінюється хмарним станом ЦІЛКОМ, без union-злиття (інакше застарілий кеш на іншому пристрої новачка «воскресив» би скинутий урок назад у хмару при наступній синхронізації).

## 7. Перевірити, що працює

- **Без ключів:** `node v2/build/build.mjs` → на сайті немає ні сторінки `account.html`, ні жодного звернення до Supabase (перевіряє `v2/mvp/tests/account-e2e.mjs`, сценарій 0).
- **З ключами:** запросити себе (крок 5.1), встановити пароль за посиланням із листа, вхід/вихід, і що прогрес уроку зберігається — і з'являється на іншому пристрої/браузері після входу тим самим акаунтом, а прогрес двох пристроїв **зливається** (пройдений урок з одного пристрою не зникає після синхронізації іншого) — та сама модель, що вже тестується на моку в `account-e2e.mjs`, сценарії 1–3.
- **Кабінет наставника:** призначити собі роль «керівник» (крок 5.2), запросити другого новачка, пройти в нього тест уроку — на `kerivnyku.html` під керівником має з'явитись картка новачка з прогресом і спробою в історії; кнопка «Скинути урок» має прибрати урок з таблиці й не дати йому повернутись зі старого пристрою новачка — перевірено сценаріями 8–10 в `account-e2e.mjs`.
- **RLS наосліп:** `node v2/mvp/tests/rls-test.mjs` (потребує локального Postgres — уже встановлений у хмарному середовищі розробки; на звичайному ноутбуці без Postgres тест чесно пише «пропущено», а не видає фальшивий «зелений»).

## Обмеження цих зрізів (чесно)

- Перевірено проти **наближеного мока** Supabase (GoTrue+PostgREST, `v2/mvp/tests/mock-supabase.mjs`) і проти **реального Postgres** для RLS-політик (`rls-test.sql`) — але не проти живого проєкту Supabase цілком (акаунти + фронтенд разом). Перший реальний вхід і запрошення варто зробити самостійно одразу після застосування міграцій.
- Синхронізація прогресу — **злиття** (union/max по кожному полю: пройдені уроки, повторення, симулятор, особиста колода — див. `mergeState()` у `v2/build/assets/account.js`), а не «останній виграє» — окрім щойно скинутого наставником прогресу (там навмисно навпаки, див. крок 6). Перевірено сценарієм «два пристрої» в `account-e2e.mjs` (сценарій 3).
- **Reload лише при вході/відкритті сторінки.** Фонове злиття (таймер що 20 с, зміна вкладки) під час активної роботи на сторінці не перезавантажує її й не чіпає поточний DOM/локальний стан (щоб не губити введення в тренажері/тесті посеред відповіді) — у хмару коректний злитий стан однаково йде щоразу, локально застосується на наступному переході. Перевірено сценарієм 9 в `account-e2e.mjs`.
- Скидання прогресу по уроку прибирає лише `state.lessons[N]` — картки повторення, позначку «розпочато» (`pos`) і симулятор цим не чіпаються навмисно (менший, зворотніший обсяг); якщо потрібно ширше скидання — поки що лише «Скинути весь прогрес».
- Особиста колода «Складний клієнт сьогодні» синхронізується в хмару разом з рештою прогресу як є (маскуються лише довгі цифри, як і раніше) — регулярка не ловить імена клієнтів у вільному тексті. Це вже позначено як відкритий ризик у `PUBLIC_DEPLOY_PLAN.md`.
