# PUBLIC_DEPLOY_PLAN — перехід курсу в публічний деплой з акаунтами

Свідома зміна курсу (підтверджено власником): статичний MVP-тренажер (гілки `mvp`, локальний сервер тренера) перетворюється на веб-застосунок з акаунтами, кабінетом наставника, редагуванням контенту і публічним деплоєм. Правила приватності лишаються чинними на новому рівні: у код, коміти й базу даних не потрапляють реальні імена/телефони клієнтів.

## 1. Стек (затверджено)

| Шар | Рішення |
|---|---|
| Акаунти й БД | **Supabase**: Postgres + Auth + Storage (аудіо діалогів) |
| Фронтенд | **Netlify**: статичний сайт (як зараз, `v2/site`) |
| Бекенд ІІ-тренера | **Netlify Functions**: ключ `ANTHROPIC_API_KEY` лише як серверна змінна оточення, ліміт на добу — per-user через таблицю в Supabase (не файл `usage.json`, як зараз) |
| Відео | Лише посилання (YouTube unlisted) в базі — без завантаження файлів |
| Ролі | `mentor` (керівник) / `newbie` (новачок) — розмежування рядків через RLS-політики Postgres |
| Сервісні акаунти | Реєструєш сам на корпоративну пошту (Supabase-проєкт, Netlify-сайт); мені передаєш лише публічні/анонімні ключі (Supabase URL + anon key) для коду — секретні ключі (service role, ANTHROPIC_API_KEY) йдуть у змінні оточення Netlify/Supabase, не в чат і не в репозиторій |

## 2. Що лишається без змін

Уся контентна частина — уроки, тренажер, симулятор, SOS, розбір у 3 рядки, вимога дослівності — не переробляється. Білд `v2/build/build.mjs` і статичні сторінки `v2/site` лишаються джерелом уроків. Новий шар додається **поверх**:
- локальний стан (`localStorage`, ключ `ikorka-mvp`) замінюється на синхронізацію з Supabase (з тим самим localStorage як офлайн-кеш і резервна копія — той самий підхід, що вже є в «Мій прогрес: файл»);
- усе, що зараз рахується на клієнті (кільце прогресу, повторення, симулятор), і далі рахується на клієнті — лише пише і читає з Supabase замість/на додачу до `localStorage`.

## 3. Схема даних (Postgres, чернетка для слайсу 1)

```
profiles         (user_id PK→auth.users, role: 'mentor'|'newbie', display_name, created_at)
lesson_progress  (user_id, lesson_n, test_passed, test_pct, test_runs, conf, updated_at)
day_progress     (user_id, day_key, learned_at)
review_cards     (user_id, card_id, step, due, lapses, added_at)
sim_progress     (user_id, scene_id, solved, first_good, tried int[], updated_at)
goals            (user_id, code, day, set_at, answered)
final_checks     (user_id, pct, pass, conf, total, weak int[], created_at)
personal_deck    (user_id, id, text, created_at)        -- див. відкрите питання нижче про PII
coach_usage      (user_id, day, calls, ok, errors, ...)  -- per-user ліміт замість спільного файлу
```
RLS: `newbie` бачить і пише лише свої рядки (`user_id = auth.uid()`); `mentor` має read-доступ до всіх (`profiles.role = 'mentor'` у політиці), write — лише до своїх.

## 4. Дороговказ по зрізах (як ти й просив — зупинка після кожного)

1. **Auth + ролі + прогрес у БД.** Supabase-проєкт, схема вище, вхід/реєстрація, `profiles.role`, міграція локального стану в Supabase-виклики (з localStorage як кеш/бекап). Приймання: новачок заходить у свій акаунт, бачить свій прогрес; вихід і вхід з іншого пристрою — прогрес той самий.
2. **Кабінет наставника.** Нова сторінка: список новачків, прогрес кожного (та сама зведена таблиця, що зараз у `kerivnyku.html`, але з БД і по всіх новачках, не по файлу одного).
3. **Контент у БД + редактор.** *(тут є розвилка — див. розділ 5 нижче, потрібне твоє рішення)*
4. **Завантаження діалогів/відео.** Форма в кабінеті наставника: текст діалогу (з валідацією на телефон/e-mail — блокує відправку), аудіо в Supabase Storage, відео — лише посилання YouTube unlisted. Наповнює порожні досі `v2/coach/personas.json` / `scenes.json`.
5. **Деплой.** Netlify (сайт + Functions), Supabase — продакшн-проєкт, секрети — у налаштуваннях обох сервісів. **Вимога (зафіксовано замовником):** контент курсу (уроки, тренажер, симулятор, SOS) доступний лише після входу — статичні сторінки `v2/site` самі по собі публічні файли на Netlify CDN, тож розмежування на рівні клієнтського JS недостатньо (URL уроку відкривається напряму). Гейтинг — **Netlify Edge Function** перед роздачею сторінок курсу: перевіряє Supabase-сесію (кука/токен), і без дійсної сесії редіректить на `account.html` замість вмісту уроку. `account.html` і статичні асети (CSS/шрифти/vendor) лишаються доступними без сесії — інакше форма входу сама не завантажиться.

## 5. Відкрите питання — редагування контенту (зріз 3)

«Редакція будь-якого тексту» — широке формулювання, і тут два різні за обсягом підходи:

**А. Точкові правки (менший обсяг, рекомендую).** Наставник редагує конкретні поля через адмінку: тексти правил, фрази «Скажи так» у SOS, розбори тестових питань, репліки сцен симулятора/тренера. Зберігається як `content_overrides` у Supabase (ключ поля + новий текст), при білді або на льоту накладається поверх того, що згенеровано з `v2/text/lessons/*.md`. Дослівність із джерела при цьому вже не перевіряється автоматично — редагування виходить з-під контролю валідатора `content-lib.mjs`, і це свідомий компроміс.

**Б. Повна CMS.** Увесь текст 12 уроків (і директиви `:::say`, `:::pairs`, `:::stat` тощо) переїжджає з markdown-файлів у Postgres, сайт рендериться з бази замість статичної збірки. Це фактично переписування всього конвеєра `v2/build/*` — набагато більший обсяг роботи, і губиться поточна система дослівної перевірки джерела.

Без твого рішення я почну зріз 3 з варіанту А (він менший, зворотний і не ламає систему перевірки дослівності) — скажи, якщо потрібен варіант Б, або уточни, які саме тексти мають редагуватись.

## 6. Ще два відкритих моменти

- **Git-процес.** Останні дві ночі діяла вимога «жодного git push і PR», тому файли передавались вручну (zip/bundle) — ти сам бачив, наскільки це незручно. Для Netlify-деплою код так чи інакше має кудись піти (або через `git push` + автодеплой Netlify з GitHub, або через `netlify deploy` CLI без пуша в origin, збираючи локально). Яким шляхом іти?
- **Гілка.** Пропоную нову гілку від `mvp` (наприклад `public-deploy`), щоб не змішувати вже протестований статичний MVP із роботою в процесі. Ок?
- **`personal_deck` і PII.** «Складний клієнт сьогодні» — це вільний текст, який новачок пише сам про свій дзвінок; зараз маскуються лише довгі цифри. Якщо ця колода теж піде в спільну БД (а не лишиться тільки в `localStorage` новачка), варто застосувати ту саму валідацію на телефон/e-mail, що й для завантажених діалогів. Регулярка не зловить ім'я клієнта в тексті — про це варто пам'ятати.
