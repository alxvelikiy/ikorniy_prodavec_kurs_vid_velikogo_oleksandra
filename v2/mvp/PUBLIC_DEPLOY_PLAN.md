# PUBLIC_DEPLOY_PLAN — перехід курсу в публічний деплой з акаунтами

Свідома зміна курсу (підтверджено власником): статичний MVP-тренажер (гілки `mvp`, локальний сервер тренера) перетворюється на веб-застосунок з акаунтами, кабінетом наставника, редагуванням контенту і публічним деплоєм. Правила приватності лишаються чинними на новому рівні: у код, коміти й базу даних не потрапляють реальні імена/телефони клієнтів.

## 1. Стек (затверджено)

| Шар | Рішення |
|---|---|
| Акаунти й БД | **Supabase**: Postgres + Auth + Storage (аудіо діалогів) |
| Фронтенд | **Netlify**: статичний сайт (як зараз, `v2/site`) |
| Бекенд ІІ-тренера | **Netlify Functions**: ключ `ANTHROPIC_API_KEY` лише як серверна змінна оточення, ліміт на добу — per-user через таблицю в Supabase (не файл `usage.json`, як зараз) |
| Відео | Лише посилання (YouTube unlisted) в базі — без завантаження файлів |
| Ролі | `mentor` (керівник) / `newbie` (новачок) — розмежування рядків через RLS-політики Postgres |
| Сервісні акаунти | Реєструєш сам на корпоративну пошту (Supabase-проєкт, Netlify-сайт); мені передаєш лише публічні/анонімні ключі (Supabase URL + anon key) для коду — секретні ключі (service role, ANTHROPIC_API_KEY) йдуть у змінні оточення Netlify/Supabase, не в чат і не в репозиторій |

## 2. Що лишається без змін

Уся контентна частина — уроки, тренажер, симулятор, SOS, розбір у 3 рядки, вимога дослівності — не переробляється. Білд `v2/build/build.mjs` і статичні сторінки `v2/site` лишаються джерелом уроків. Новий шар додається **поверх**:
- локальний стан (`localStorage`, ключ `ikorka-mvp`) замінюється на синхронізацію з Supabase (з тим самим localStorage як офлайн-кеш і резервна копія — той самий підхід, що вже є в «Мій прогрес: файл»);
- усе, що зараз рахується на клієнті (кільце прогресу, повторення, симулятор), і далі рахується на клієнті — лише пише і читає з Supabase замість/на додачу до `localStorage`.

## 3. Схема даних (Postgres, чернетка для слайсу 1)

```
profiles         (user_id PK→auth.users, role: 'mentor'|'newbie', display_name, created_at)
lesson_progress  (user_id, lesson_n, test_passed, test_pct, test_runs, conf, updated_at)
day_progress     (user_id, day_key, learned_at)
review_cards     (user_id, card_id, step, due, lapses, added_at)
sim_progress     (user_id, scene_id, solved, first_good, tried int[], updated_at)
goals            (user_id, code, day, set_at, answered)
final_checks     (user_id, pct, pass, conf, total, weak int[], created_at)
personal_deck    (user_id, id, text, created_at)        -- див. відкрите питання нижче про PII
coach_usage      (user_id, day, calls, ok, errors, ...)  -- per-user ліміт замість спільного файлу
```
RLS: `newbie` бачить і пише лише свої рядки (`user_id = auth.uid()`); `mentor` має read-доступ до всіх (`profiles.role = 'mentor'` у політиці), write — лише до своїх.

## 4. Дороговказ по зрізах (як ти й просив — зупинка після кожного)

1. **Auth + ролі + прогрес у БД.** ✅ Готово (+ правки: запрошення замість signup, злиття замість «останній виграє», вендоринг supabase-js). Supabase-проєкт, схема вище, вхід лише за запрошенням, `profiles.role`, синхронізація локального стану з Supabase (з localStorage як кеш/бекап).
2. **Кабінет наставника.** ✅ Готово. `kerivnyku.html` (блок «Новачки (хмара)», видимий лише керівнику): список новачків, прогрес кожного по днях/уроках, дата останньої активності, історія спроб тесту й тренажера (`attempts` — append-only, не лише останній результат), скидання прогресу (весь або по уроку) через `reset_progress()` з коректною реакцією клієнта на застарілий кеш (`generation`). Деталі — `SUPABASE_SETUP.md`, розділ 6.
3. **Контент у БД + редактор.** ❌ Знято з дорожньої карти (рішення власника, 2026-09-27, див. розділ 5 нижче) — окремої адмінки на сайті не буде.
4. **Завантаження діалогів/відео.** ❌ Знято з дорожньої карти тим самим рішенням — окремої форми завантаження на сайті не буде.
5. **Деплой.** ✅ Готово (код). Netlify (сайт + звичайна Function для ІІ-тренера + Edge Function для гейтингу), Supabase — той самий продакшн-проєкт, що й у зрізах 1–2, секрети — у Environment variables Netlify. **Вимога (зафіксовано замовником):** контент курсу (уроки, тренажер, симулятор, SOS) доступний лише після входу — статичні сторінки `v2/site` самі по собі публічні файли на Netlify CDN, тож розмежування на рівні клієнтського JS недостатньо (URL уроку відкривається напряму). Гейтинг — **Netlify Edge Function** (`netlify/edge-functions/gate-content.js`) перед роздачею сторінок курсу: перевіряє Supabase-сесію через куку `sb_at` (дзеркало access_token з localStorage, синхронізується `account.js`), звіряючи її з GoTrue (`/auth/v1/user`), і без дійсної сесії редіректить на `account.html` замість вмісту уроку. `account.html` і статичні асети (CSS/шрифти/vendor) лишаються доступними без сесії — інакше форма входу сама не завантажиться. ІІ-тренер переїхав з локального `v2/coach/server.mjs` на `netlify/functions/coach.mjs` — той самий захищений промпт і валідатори, per-user ліміт тепер у Supabase (`coach_usage`, `supabase/migrations/0003_coach_usage.sql`) замість спільного файлу `usage.json`, який на serverless-функції однаково не пережив би між викликами. Деталі підключення в Netlify UI — `SUPABASE_SETUP.md`, розділ 8. **Жива перевірка проти реального Netlify/Anthropic — власник проводить сам** (це середовище розробки не має мережевого доступу до `api.netlify.com`/`api.anthropic.com`).

## 5. Редагування контенту (зрізи 3–4) — рішення власника: без адмінки

Власник розглянув розвилку нижче (варіант А/Б) і **вирішив інакше, ніж обидва варіанти**: окремої сторінки-адмінки на сайті не буде взагалі — ні зараз, ні згодом у цьому проєкті. Редагування текстів уроків, фраз SOS, сцен симулятора/тренера, і будь-яке майбутнє завантаження аудіо/відео — все це відбувається так само, як велась уся попередня робота над курсом: власник просить конкретну правку в Claude Code, і зміна вноситься напряму у файли репозиторію (`v2/text/lessons/*.md`, `v2/mvp/content/*.json`, `v2/coach/data/*.json` тощо), проходить той самий валідатор дослівності (`content-lib.mjs`) і той самий автотест, і йде в комміт. Це залишає систему перевірки дослівності джерела недоторканою (варіант Б її ламав) і не додає окремого шару UI/авторизації для адмінки (варіант А вимагав би цього).

Розвилка нижче лишена в документі для історії рішення:

**А. Точкові правки через адмінку (не обрано).** Наставник редагує конкретні поля через окрему сторінку: тексти правил, фрази «Скажи так» у SOS, розбори тестових питань, репліки сцен симулятора/тренера. Зберігалось би як `content_overrides` у Supabase (ключ поля + новий текст), при білді або на льоту накладалося б поверх того, що згенеровано з `v2/text/lessons/*.md`. Дослівність із джерела при цьому вже не перевірялась би автоматично — редагування вийшло б з-під контролю валідатора `content-lib.mjs`.

**Б. Повна CMS (не обрано).** Увесь текст 12 уроків (і директиви `:::say`, `:::pairs`, `:::stat` тощо) переїжджав би з markdown-файлів у Postgres, сайт рендерився б з бази замість статичної збірки. Найбільший обсяг роботи, і губилась би поточна система дослівної перевірки джерела.

## 6. Ще один відкритий момент

- **Git-процес і гілка.** ✅ Вирішено. Гілка `public-deploy` (від `mvp`) — саме вона. Заборону на `git push` для цієї гілки власник зняв особисто (bundle/zip-передача виявилась ненадійною) — код іде в GitHub через звичайний `git push origin public-deploy`, Netlify деплоїть автоматично з GitHub (крок 8.1 у `SUPABASE_SETUP.md`).
- **`personal_deck` і PII.** «Складний клієнт сьогодні» — це вільний текст, який новачок пише сам про свій дзвінок; зараз маскуються лише довгі цифри. Ця колода йде в спільну БД (синхронізується як частина `progress`, разом з рештою прогресу — зріз 1) без додаткової валідації на ім'я клієнта — регулярка ловить лише довгі цифри, не імена в вільному тексті.
